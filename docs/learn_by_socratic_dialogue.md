## Act I — First Encounter: What Is Uncertainty, and Why Should Code Care?

**Artemis:** Ophelia, I've been writing Scala for years, and I've always dealt with single values—a temperature is 72 degrees, a speed is 65 miles per hour, a conversion rate is 12 percent. But I've come across this library called Uncertain[T], and it seems to want me to rethink all of that. What is it, exactly?

**Ophelia:** A fine place to start, Artemis. Tell me—when you say "the temperature is 72 degrees," how confident are you in that number?

**Artemis:** Well… the sensor has some error margin. It might really be 70 or 74. But I just use the number the sensor gives me.

**Ophelia:** And when you do arithmetic with that number—say, computing the average temperature over a day, or checking if it exceeds a threshold—do you account for that error?

**Artemis:** Not usually. I'd have to write separate code to track error bars, propagate variance, maybe do a Monte Carlo simulation by hand. It's a lot of work.

**Ophelia:** That is precisely the problem Uncertain[T] solves. Instead of `val temperature: Double = 72.0`, you write `val temperature: Uncertain[Double] = Uncertain.normal(72.0, 3.0)`. Now the temperature is not a point; it is a *distribution*—a bell curve centered at 72 with a standard deviation of 3. And you can do arithmetic with it *as if it were a regular value*, and the uncertainty propagates automatically.

**Artemis:** So it's a container—like `Option[T]` wraps a value that might be absent, `Uncertain[T]` wraps a value that might be… anything within a range?

**Ophelia:** A beautiful analogy. Option[T] represents the uncertainty of *existence*—"is there a value here?" Uncertain[T] represents the uncertainty of *magnitude*—"what value is here?" And just as Option has `map` and `flatMap`, so does Uncertain. It is a monad.

**Artemis:** A monad! So I can use for-comprehensions?

**Ophelia:** Indeed. Consider estimating how long a project will take:

```scala
import mostly.uncertaintee.Uncertain
import mostly.uncertaintee.syntax.*

val frontend = Uncertain.triangular(5, 10, 20)  // days
val backend  = Uncertain.triangular(8, 15, 30)
val testing  = Uncertain.triangular(3, 5, 10)

val total = frontend + backend + testing
```

Each of those is a triangular distribution—a minimum, a most-likely, and a maximum. Adding them produces a new `Uncertain[Double]` that represents the distribution of possible total durations. No hand-rolled statistics needed.

**Artemis:** That's remarkably clean. But how do I get answers out of it?

**Ophelia:** You *sample*. You call `total.sample()` to draw one random realization, or `total.mean(sampleCount = 100_000)` to estimate the average, or `total.percentiles(sampleCount = 100_000)` to get the full percentile breakdown. The key insight is that Uncertain[T] is evaluated via *Monte Carlo simulation*—each call to `sample()` runs the entire computation graph, drawing fresh random numbers from the underlying distributions.

**Artemis:** So the more samples I take, the more accurate my statistics?

**Ophelia:** Precisely. The library's philosophy is: you trade compute time for precision. Under 10,000 samples may be rough; 100,000 is often a sweet spot; a million might be overkill. You have to calibrate for your specific use case.

## Act II — Creating Distributions: The Vocabulary of Uncertainty

**Artemis:** You mentioned `normal` and `triangular`. What other distributions does the library offer?

**Ophelia:** The library provides a rich vocabulary. Let me walk you through them in families.

For **continuous distributions**, you have:
- `Uncertain.normal(mean, stdDev)` — the classic bell curve, for measurement error, natural phenomena
- `Uncertain.uniform(min, max)` — every value in the range equally likely
- `Uncertain.triangular(min, peak, max)` — when you know the best, worst, and most likely case
- `Uncertain.exponential(rate)` — for time-between-events, memoryless processes
- `Uncertain.beta(alpha, beta)` — the workhorse of Bayesian statistics, modeling probabilities of probabilities
- `Uncertain.kumaraswamy(a, b)` — similar to Beta but with a closed-form inverse CDF
- `Uncertain.rayleigh(scale)` — for magnitudes of two-dimensional random vectors

For **discrete distributions**:
- `Uncertain.bernoulli(probability)` — true/false with a given probability, the simplest coin flip
- `Uncertain.binomial(trials, probability)` — count of successes in N trials
- `Uncertain.poisson(lambda)` — count of events in a fixed interval
- `Uncertain.geometric(probability)` — number of trials until first success
- `Uncertain.negativeBinomial(r, probability)` — number of failures before r successes
- `Uncertain.categorical(Map(...))` — pick from named outcomes with weights
- `Uncertain.empirical(data)` — resample from observed data

And several **convenience constructors**:
- `Uncertain.always(value)` — wraps a constant in the Uncertain type, for mixing certain and uncertain values
- `Uncertain.mixture(Map(...))` — weighted combination of multiple distributions
- `Uncertain.fromRange(1 to 6)` — uniform over a Scala Range
- `Uncertain.fromInverseCdf(...)` — build any custom distribution from its inverse CDF

**Artemis:** That `fromInverseCdf` is interesting. So I could model *any* distribution?

**Ophelia:** Yes! If you can express the inverse of the cumulative distribution function—the function that maps a probability in [0,1] to a value—then Uncertain can sample from it using the inverse transform method. It generates a uniform random number and feeds it through your function. This is the mathematical foundation underlying many of these distributions.

**Artemis:** And `Uncertain.always`—why would I need to wrap a constant?

**Ophelia:** Because the type system demands it. If you're composing uncertain values in a for-comprehension and one component is known exactly, you still need it to be `Uncertain[T]` for the types to align. `Uncertain.always(60.0)` always samples to 60.0, but it participates in the computation graph like any other node.

## Act IV — The Monadic Heart: map, flatMap, and For-Comprehensions

**Artemis:** You said Uncertain is a monad. Let me make sure I understand. `map` transforms the value inside the container, and `flatMap` chains dependent uncertain computations?

**Ophelia:** Yes. Let's explore each carefully.

`.map(f)` applies a *pure* function to each sample. If you have an uncertain speed in miles per hour and want kilometers:

```scala
val speedMph = Uncertain.uniform(50, 70)
val speedKph = speedMph.map(_ * 1.60934)
```

The resulting `speedKph` preserves the same source of randomness as `speedMph`—they are correlated. The mapping is deterministic: given a sample of 60 mph, the corresponding kph is always 96.56.

You can also `.map` to a completely different type:

```scala
val temperatureF = Uncertain.normal(75, 10)
val comfortLevel = temperatureF.map { temp =>
  if (temp > 85) "Hot"
  else if (temp > 65) "Comfortable"
  else "Cold"
}
```

Now `comfortLevel` is `Uncertain[String]`. You've gone from a continuous distribution to a categorical one via mapping.

**Artemis:** And `flatMap`?

**Ophelia:** `flatMap` is for *conditional* or *dependent* uncertainty. The function you pass takes a concrete sample and returns a *new* Uncertain value. This lets you model situations where one random variable determines the *distribution* of the next.

```scala
val weatherIsGood = Uncertain.bernoulli(0.7)

val attendance = weatherIsGood.flatMap { isGood =>
  if (isGood) Uncertain.normal(100, 10)
  else Uncertain.normal(60, 15)
}
```

Here, the attendance distribution *depends on* the weather. In good weather, we expect 100 ± 10 people; in bad weather, 60 ± 15. The resulting `attendance` captures the full joint distribution.

**Artemis:** And for-comprehensions compose both?

**Ophelia:** Exactly. This:

```scala
val total = for {
  f <- frontend
  b <- backend
  t <- testing
} yield f + b + t
```

desugars to nested `flatMap` and `map` calls. Each variable is drawn from its distribution, the correlation structure is maintained, and `total` is a new Uncertain[Double] representing the sum.

**Artemis:** Can I build case classes this way?

**Ophelia:** Absolutely. It's one of the most powerful patterns:

```scala
case class Rectangle(width: Double, height: Double) {
  def area: Double = width * height
}

val uncertainRect: Uncertain[Rectangle] = for {
  w <- Uncertain.normal(10, 1)
  h <- Uncertain.normal(5, 0.5)
} yield Rectangle(w, h)

val uncertainArea = uncertainRect.map(_.area)
```

You've created an `Uncertain[Rectangle]`—a distribution over rectangles. And from that, an uncertain area. The Scala type system ensures everything composes.

## Act V — The Deepest Guarantee: Correlation Preservation

**Artemis:** You keep mentioning correlation. Can you show me why it matters?

**Ophelia:** This is arguably the library's most important property, and the one that distinguishes it from naive Monte Carlo approaches. Consider:

```scala
val x = Uncertain.normal(10, 2)

val uncorrelated = Uncertain.normal(10, 2) - Uncertain.normal(10, 2)
val correlated   = x - x
```

`uncorrelated.sample()` will give you values like 1.5, -0.8, 2.1—because each `Uncertain.normal(10, 2)` creates a *separate* source of randomness. But `correlated.sample()` will *always* return exactly 0.0, because both references to `x` in the for-comprehension see the same sample.

**Artemis:** How does it do that? How does it know that two references to `x` should get the same sample?

**Ophelia:** This is where the **computation tree** comes in—the internal engine of the library. Let me explain.

When you call `Uncertain.normal(10, 2)`, the library creates a **leaf node** with a unique ID (a Long from an AtomicLong counter) and a sampling function. When you compose these with `map` and `flatMap`, you build a tree: `ComputationMapping` nodes for maps, `ComputationFlatMapping` nodes for flatMaps, `ComputationPure` nodes for constants.

When you call `.sample()`, the tree is evaluated. Crucially, each evaluation creates a fresh **SampleContext**—a mutable `LongMap[Any]` that serves as a memoization cache. When a `ComputationLeaf` is encountered, the context checks: "Have I already sampled this leaf ID?" If yes, it returns the cached value. If no, it samples, caches, and returns.

**Artemis:** So the unique IDs are the identity mechanism? If I write `x - x`, both sides of the subtraction trace back to the same leaf with the same ID, so the SampleContext returns the same sample for both?

**Ophelia:** Precisely. But if I write `Uncertain.normal(10, 2) - Uncertain.normal(10, 2)`, each `normal` call creates a *separate* leaf with a *different* ID, so they sample independently.

**Artemis:** What about in a for-comprehension? If I write:

```scala
for {
  a <- x
  b <- x
} yield a - b
```

The desugaring is `x.flatMap(a => x.map(b => a - b))`. The inner `x.map(...)` creates a new `ComputationMapping` node whose source is the *same* leaf as the outer `x.flatMap(...)`. When evaluated with a single SampleContext, both resolve to the same cached sample?

**Ophelia:** Exactly right. The correlation is structural—it comes from the *identity* of the computation tree nodes, not from any explicit tracking by the user. The user simply writes natural Scala code with for-comprehensions, and the correlation is preserved automatically.

**Artemis:** This is the guarantee from the Microsoft Research paper, isn't it?

**Ophelia:** Yes. The paper is "Uncertain\<T\>: A First-Order Type for Uncertain Data." The core insight is that by treating uncertain values as *deferred computations* with memoized identity, you get correlation preservation "for free." This library is a Scala implementation of that idea.

## Act VI — Inside the Engine: The Computation Tree

**Artemis:** I want to understand the computation tree more deeply. What are all the node types?

**Ophelia:** There are exactly four:

1. **`ComputationPure(value)`** — a constant. Used by `Uncertain.always(x)`. Returns the value directly; no caching needed because it's always the same.

2. **`ComputationLeaf(id, sampler)`** — a source of randomness. Created by `Uncertain(samplerFn)`. The `id` is a `Long` from a global `AtomicLong` counter. The `sampler` is a `() => T` that draws from the underlying distribution. The SampleContext memoizes by `id`.

3. **`ComputationMapping(source, transform)`** — a deterministic transformation (`.map`). Stores the upstream tree and the function to apply. When evaluated, it evaluates the source and applies the transform.

4. **`ComputationFlatMapping(source, transformToUncertain)`** — a monadic bind (`.flatMap`). Evaluates the source, passes the result to the function (which returns a new `Uncertain`), then evaluates *that* uncertain's computation tree—crucially, *within the same SampleContext*.

**Artemis:** That last point is critical—the inner uncertain from a `flatMap` shares the same SampleContext?

**Ophelia:** Yes! That's what makes correlation preservation work across `flatMap` boundaries. If inside a `flatMap` you reference an `Uncertain` that was defined outside, it will use the same SampleContext, and any leaf that was already sampled will return the cached value.

**Artemis:** What about stack safety? If I chain hundreds of `flatMap` calls, won't I overflow the stack?

**Ophelia:** The evaluation uses **trampolining** via Scala's `scala.util.control.TailCalls`. The `evaluateTrampoline` method returns `TailRec[T]` instead of `T` directly. For `ComputationFlatMapping`, it uses `TailCalls.flatMap` to chain without growing the stack. Then `.result` at the top level unwinds the trampoline. The library includes explicit stack safety tests for deeply nested computations.

**Artemis:** And I noticed a comment about "Map Fusion" in the `map` implementation?

**Ophelia:** Excellent eye. When you call `.map(f)` on something that is already a `ComputationMapping(source, g)`, instead of creating `ComputationMapping(ComputationMapping(source, g), f)`, the library *fuses* them into `ComputationMapping(source, g.andThen(f))`. This reduces tree depth and object allocation. `x.map(f).map(g)` becomes a single node instead of two nested ones.

**Artemis:** But this only works for `map`, not for `flatMap`?

**Ophelia:** Correct. `flatMap` creates a new computation tree whose structure can't be known at composition time, so fusion isn't possible there.

## Act VII — The Arithmetic Layer: Operating Like Numbers

**Artemis:** The README shows `frontend + backend + testing` — just using `+` on Uncertain values. How does that work without Uncertain extending a numeric type?

**Ophelia:** Through Scala 3's **extension methods**. The `ArithmeticOps` trait defines extensions on `Uncertain[T]` for `+`, `-`, `*`, `/`, `%`, and `unary_-`, where `T` is a supported numeric type (Double, Float, Long, Int, Short, Byte, Char). These are defined via `transparent inline` match expressions that handle every combination of numeric types, following Scala's widening rules.

**Artemis:** Every combination? That sounds like a lot of boilerplate.

**Ophelia:** It is—and intentionally so. The library uses Scala 3's `transparent inline` to resolve at compile time which operation to perform. For `Uncertain[Double] + Uncertain[Int]`, the result is `Uncertain[Double]`, following the standard JVM numeric promotion rules. This gives you type-safe arithmetic with no runtime overhead from type dispatch.

**Artemis:** And it works with plain numbers on the left? Like `5.0 + uncertainValue`?

**Ophelia:** Yes. There are separate extension methods on `SupportedNum` (the union type `Double | Float | Long | Int | Char | Short | Byte`) that handle the case where a plain number is on the left-hand side. To disambiguate the overloads, the library uses "dummy" sealed traits as implicit evidence—`Left2Right_Uncertain_Uncertain` and `Left2Right_SupportedNum_Uncertain`—which are always in scope when you import the syntax.

**Artemis:** Clever. So `3.5 * uncertain` just works?

**Ophelia:** Exactly. It compiles to `uncertain.map(3.5 * _)` under the hood.

## Act VIII — Boolean Logic and Decision Making

**Artemis:** What about comparisons? The README shows `speed > 60` returning `Uncertain[Boolean]`.

**Ophelia:** The `ComparisonOps` trait provides `>`, `<`, `>=`, `<=`, `gt`, `lt`, `gte`, `lte` as extension methods on `Uncertain[T]` where `T` has an `Ordering`. These work against both constant values and other `Uncertain` values. Each comparison produces an `Uncertain[Boolean]`.

**Artemis:** And then what do I do with an `Uncertain[Boolean]`? I can't use it in an `if` statement directly.

**Ophelia:** Correct—and that's by design. An `Uncertain[Boolean]` doesn't have a single truth value; it has a *probability* of being true. The `BooleanOps` trait gives you several ways to extract a decision:

- `.probability(sampleCount)` — estimates P(true) by sampling and averaging
- `.isProbable(sampleCount)` — tests whether P(true) > 0.5 with statistical confidence
- `.probabilityExceeds(exceeds, sampleCount)` — tests P(true) > threshold

**Artemis:** How does `isProbable` work statistically? It's not just checking if the count is over 50%, is it?

**Ophelia:** No—it uses the **Sequential Probability Ratio Test** (SPRT). This is a hypothesis testing procedure that can reach a decision *early* if the evidence is overwhelming. It has parameters `alpha` (Type I error rate) and `beta` (Type II error rate), both defaulting to 0.05. The SPRT computes a log-likelihood ratio after each sample and compares it to decision boundaries derived from alpha and beta. If the boundaries aren't reached within the sample budget, it falls back to a normal approximation with a z-test.

**Artemis:** So it's not just brute-force sampling—it's an actual statistical test with controlled error rates?

**Ophelia:** Exactly. And it returns a `HypothesisResult` case class with the decision, estimated probability, confidence level, and number of samples actually used. The convenience methods like `isProbable` just extract the `decision` field.

**Artemis:** And `Uncertain[Boolean]` supports logical operators?

**Ophelia:** Yes: `&&`, `||`, and `unary_!`. These combine uncertain booleans sample-by-sample via for-comprehensions. And there's an `indicator` method that converts `Uncertain[Boolean]` to `Uncertain[Int]` (0 or 1)—the mathematical indicator function, which is used internally for probability estimation.

## Act IX — filter, Option, and the Correlation Dilemma

**Artemis:** I see that `Uncertain` has a `filter` method, but it returns `Uncertain[Option[T]]` instead of `Uncertain[T]`. That seems unusual. Why not just reject samples that don't pass and resample?

**Ophelia:** This is one of the most thoughtful design decisions in the library, and the Scaladoc explains it at length. The answer is: *rejection sampling would break correlation*.

Consider:

```scala
val x = Uncertain.normal(0, 1)
val positive = x.rejectionFilter(_ > 0)  // hypothetical broken version
```

If `positive` used rejection sampling (resample until positive), then `positive.sample()` would depend on *how many rejections occurred*, which varies randomly. Two references to `positive` in the same computation could end up with different samples, violating the core guarantee.

**Artemis:** Oh! Because the SampleContext memoizes by leaf ID, and rejection sampling would need to call the sampler a variable number of times…

**Ophelia:** Exactly. So instead, `filter` wraps the result: `Some(value)` if the predicate passes, `None` if it fails. This is a *deterministic* transformation—same input, same output—so correlation is preserved. Two references to `maybePositive` in the same evaluation will always produce the same `Some(x)` or the same `None`.

**Artemis:** And then how do I handle the `None` cases?

**Ophelia:** The `OptionOps` trait provides two methods:
- `.orElse(fallback)` — provides an alternative `Uncertain[T]` to sample from when `None`
- `.getOrElse(default)` — provides a constant default value for `None`

And in `StatisticalOps`:
- `.probabilityOfSuccess(sampleCount)` — what fraction of samples pass the filter?
- `.probabilityOfFailure(sampleCount)` — what fraction are rejected?

**Artemis:** So `filter` plus `orElse` gives me "try this distribution, and if it doesn't satisfy my constraints, fall back to another." That's compositional.

**Ophelia:** Precisely. And notice the elegance: the library could have special-cased this, but instead it composes naturally from `map` (to lift into Option), `flatMap` (for orElse), and the general monadic structure.

## Act X — Statistical Analysis: Measuring the Unmeasured

**Artemis:** Once I have an Uncertain value, what statistical tools can I apply?

**Ophelia:** The `StatisticalOps` trait provides:

For any `Uncertain[T]`:
- `.mode(sampleCount)` — the most common sample (best for discrete)
- `.histogram(sampleCount)` — frequency map of all sample values
- `.entropy(sampleCount)` — information entropy in bits

For `Uncertain[T]` with `Numeric[T]`:
- `.mean(sampleCount)` / `.expectedValue(sampleCount)` — the average
- `.standardDeviation(sampleCount)` — sample standard deviation with Bessel's correction
- `.populationStandardDeviation(sampleCount)` — without Bessel's correction
- `.kurtosis(sampleCount)` — excess kurtosis with classification

For `Uncertain[T]` with `Ordering[T]`:
- `.confidenceInterval(confidence, sampleCount)` — percentile-based CI
- `.cdf(value, sampleCount)` — estimated P(X ≤ value)

**Artemis:** Tell me about kurtosis. That seems unusually sophisticated.

**Ophelia:** It is! Kurtosis measures "tailedness"—how heavy the tails of the distribution are compared to a normal distribution. The library computes it using a single-pass, O(1)-memory Welford-Knuth streaming algorithm. No intermediate collections are created; it iterates directly over the sample generator.

The result isn't just a number—it's a typed `Kurtosis` ADT:
- `Kurtosis.Mesokurtic(value)` — normal-like tails (excess kurtosis ≈ 0)
- `Kurtosis.Leptokurtic(value)` — heavy tails (excess kurtosis > 0), like exponential distributions
- `Kurtosis.Platykurtic(value)` — light tails (excess kurtosis < 0), like uniform distributions
- `Kurtosis.Undefined` — when standard deviation is zero (constant distribution)

You can pattern match on it, which is delightful.

**Artemis:** That's elegant. What's the `mesokurticTolerance` parameter?

**Ophelia:** It's the threshold for classification. Values of excess kurtosis within ±0.5 of zero are classified as Mesokurtic by default. This accounts for sampling noise—you'd never get *exactly* zero from Monte Carlo estimation.

## Act XI — Quantiles: The Universal Summary

**Artemis:** I see a whole `quantiles` package. What's the design there?

**Ophelia:** Quantiles are the library's answer to "how do I summarize a distribution?" The `Quantiles[T]` trait represents N-quantile boundary values—the points that divide the distribution into N equal-probability intervals.

There are specific type aliases for common cases:
- `Tertiles[T]` — 3 intervals, 4 boundary values
- `Quartiles[T]` — 4 intervals, 5 boundary values
- `Quintiles[T]` — 5 intervals, 6 boundary values
- `Deciles[T]` — 10 intervals, 11 boundary values
- `Percentiles[T]` — 100 intervals, 101 boundary values

You compute them from an Uncertain:

```scala
val p = myUncertain.percentiles(sampleCount = 100_000)
val median = p(50)
val p95 = p(95)
```

**Artemis:** The `apply(index)` method accesses boundary values. So `p(0)` is the minimum and `p(100)` is the maximum?

**Ophelia:** Yes. And you can convert between them—`Percentiles` has `.toQuartiles`, `.toQuintiles`, `.toDeciles`. You can also get `.boundaryValues` as a list, or `.toMap` as an index-to-value map.

**Artemis:** But quantiles are just a summary. Can I go back to an Uncertain from quantiles?

**Ophelia:** Yes! And this is where it gets fascinating. The library provides four reconstruction strategies:

1. **`reconstructDiscrete`** — creates an empirical distribution that samples uniformly from the boundary values themselves. Values *between* boundaries are lost. Best for inherently discrete data.

2. **`reconstructStep`** — piecewise uniform within each interval. Like a histogram. Each quantile interval gets equal probability mass, and within that interval, values are sampled uniformly.

3. **`reconstructLinear`** — piecewise linear interpolation through the boundary values. The recommended default for continuous data. Uses the inverse CDF method.

4. **`reconstructSmooth`** — monotonic cubic Hermite spline interpolation using the Fritsch-Carlson method. Produces a C1-continuous curve that passes through all boundary points. This preserves monotonicity—critical for a CDF—and gives the smoothest reconstruction.

**Artemis:** The smooth spline sounds complex. What's the Fritsch-Carlson method?

**Ophelia:** It's an algorithm for constructing monotone-preserving cubic splines. The library implements it internally in `SmoothSpline.scala`. It:
1. Computes slopes between adjacent points
2. Estimates tangents at each point using a weighted harmonic mean
3. Adjusts tangents to ensure monotonicity (the Fritsch-Carlson correction)
4. Constructs cubic Hermite polynomial segments evaluated via Horner's method for numerical stability

The result is a spline where `CubicSegment(a, b, c, d)` represents `a + t*(b + t*(c + t*d))` for parameter t in [0,1]. The clamping of t prevents extrapolation issues.

**Artemis:** So quantiles serve a dual purpose: statistical summary *and* serialization format?

**Ophelia:** Exactly right, and that leads us to the Circe module.

## Act XII — The Circe Module: Serializing Uncertainty

**Artemis:** How do you serialize an `Uncertain[T]` to JSON? The distribution could be anything—a normal, a mixture, a chain of flatMaps…

**Ophelia:** You can't serialize the *computation graph* directly—that would require serializing arbitrary closures, which is a well-known impossibility. Instead, you serialize via quantiles.

The `uncertain-tee-circe` module provides encoders and decoders that work through quantile boundaries:

```scala
import mostly.uncertaintee.circe.*
import io.circe.syntax.*

// Encode: sample the distribution, compute quantiles, write boundary values
val json = myUncertain.toJson(sampleCount = 100_000, quantilesToSerialize = 100)
// { "quantiles": { "boundaryValues": [v0, v1, ..., v100] } }

// Decode: read boundary values, reconstruct a distribution
val Right(reconstructed) = Uncertain.fromJsonAsSmoothDistribution(json)
```

**Artemis:** So it's lossy? You lose information during serialization?

**Ophelia:** Necessarily. You're compressing an infinite-dimensional object (a distribution) into a finite representation (101 numbers for percentiles). But the loss is controllable:
- More quantile intervals → higher fidelity (at the cost of larger JSON)
- More samples → more accurate quantile boundaries
- Smoother reconstruction → better approximation of the original shape

The Scaladoc recommends 100,000+ samples for serialization, because this is the operation where you lose the most precision.

**Artemis:** And the four reconstruction methods are available as four separate decoders?

**Ophelia:** Yes: `decoderUncertainDiscrete`, `decoderUncertainStep`, `decoderUncertainLinear`, `decoderUncertainSmooth`. The choice of decoder is a decision the consumer makes based on what they know about the data. The encoder is the same regardless.

**Artemis:** What about encoding Quantiles directly, without wrapping in an Uncertain?

**Ophelia:** That's supported too. `Quantiles[T]` has its own encoder/decoder: `encoderQuantiles` and `decoderQuantiles`. You can also do `Quantiles.fromJson(json)`.

## Act XIII — The Cats Module: Typeclass Lawfulness

**Artemis:** The `uncertain-tee-cats` module provides typeclass instances. What exactly?

**Ophelia:** It provides:
- `Functor[Uncertain]` — delegating to `.map`
- `StackSafeMonad[Uncertain]` — with `pure` as `Uncertain.always`, `flatMap` and `map` delegating to the core methods. Note: it's `StackSafeMonad`, reflecting the trampolined evaluation.
- `Monoid[Uncertain[T]]` — when `T` has a Cats `Monoid`. `empty` is `Uncertain.always(Monoid[T].empty)`, and `combine` lifts the monoidal combine via `flatMap`/`map`.
- `Semigroup[Uncertain[T]]` — when `T` has a `Semigroup` but *not* a `Monoid` (using `NotGiven[Monoid[T]]` to avoid ambiguity). Combines element-wise.
- `Group[Uncertain[T]]` — when `T` has a Cats `Group`, providing `inverse` and `combine`.

**Artemis:** So I could use `|+|` to combine uncertain values?

**Ophelia:** Yes! With the Cats instances imported:

```scala
import cats.syntax.all.*
import mostly.uncertaintee.cats.*

val a = Uncertain.normal(10, 2)
val b = Uncertain.normal(5, 1)
val combined = a |+| b  // Uses Monoid[Double] to add them
```

**Artemis:** Are the monad laws actually tested?

**Ophelia:** The test file imports `cats.laws` and `discipline-munit`, so yes—the laws are verified via the Cats discipline testing framework. Functor laws, Monad laws, etc.

**Artemis:** One subtlety—the instances use `implicit` rather than `given`. Why?

**Ophelia:** The library includes a `WhyIsThisImplicitAndNotGiven` style documentation object that explains this decision. In Scala 3, a wildcard import (`import foo.*`) imports `implicit` vals but *not* `given` instances—you need `import foo.{given, *}` for those. Since most Scala developers expect wildcard imports to bring in everything, the library uses `implicit` to avoid a common source of confusion. They plan to switch when a future Scala version changes this behavior.

## Act XIV — The ZIO Module: A Different Functional Ecosystem

**Artemis:** And the ZIO Prelude integration?

**Ophelia:** The `uncertain-tee-zio` module provides a single combined typeclass instance that satisfies `CovariantIdentityBoth[Uncertain]` and `IdentityFlatten[Uncertain]`. These are ZIO Prelude's abstractions for functor-like and monad-like things.

- `.map` delegates to `Uncertain.map`
- `.both` combines two Uncertains into a pair using `.product`
- `.flatten` delegates to `flatMap(identity)`
- `.any` returns `Uncertain.always(())`

There's also a `Debug[Uncertain[A]]` instance, which presents an interesting philosophical question annotated right in the code: what does debugging look like for a random variable? The library opts for a static representation—`Uncertain[ClassName]`—without sampling, since sampling would break determinism in debug output.

**Artemis:** That's a thoughtful choice. Debug output that changes every time you look at it would be maddening.

## Act XV — The ScalaCheck Module: Testing Uncertainty

**Artemis:** Property-based testing seems like a natural fit. What does the ScalaCheck module provide?

**Ophelia:** Three things:

**First**, `UncertainInstances` — pre-built `Gen[Uncertain[T]]` generators for all major distributions. `gaussianUncertain()`, `uniformUncertain()`, `triangularUncertain()`, `exponentialUncertain()`, `kumaraswamyUncertain()`, `rayleighUncertain()`, `empiricalUncertain()`. And a combined `uncertainDouble` that randomly picks from all of these.

Each generator is carefully constructed: it generates random parameters (mean, stdDev, etc.) *and* a random `scala.util.Random` seed, so each generated `Uncertain` has its own deterministic RNG.

**Second**, `GenUncertainOps` — bidirectional conversion between `Gen` and `Uncertain`:
- `Gen.fromUncertain(uncertain)` — wraps an Uncertain's samples as a ScalaCheck Gen
- `Uncertain.fromGen(gen)` — wraps a ScalaCheck Gen as an Uncertain

The Scaladoc includes an important caveat: because Uncertain manages its own RNG state, ScalaCheck's seed-based reproducibility doesn't apply to these generators. You need to use a seeded `scala.util.Random` for determinism.

**Third**, `PropUncertainOps` — a `Prop.forAllUncertain(uncertain, samples)(predicate)` helper that checks a predicate against multiple samples and reports failures with the actual failing values.

**Artemis:** So I can write properties like "for all samples from this uncertain distribution, the result should be positive"?

**Ophelia:** Exactly. And with the `UncertainInstances`, you can write higher-order properties like "for any Gaussian distribution with any mean and standard deviation, the mean of 10,000 samples should be close to the specified mean."

## Act XVI — The Squants Module: Uncertainty with Physical Units

**Artemis:** This is the one I'm most curious about. How does Uncertain[T] work with SI units?

**Ophelia:** The `uncertain-tee-squants` module integrates with the Squants library, which provides type-safe physical quantities like `Length`, `Mass`, `Velocity`, `Temperature`, etc.

At its core is the `QuantityStatisticallyConvertible[Q]` typeclass. It defines two operations: converting a `Quantity[Q]` to a `Double` (in a chosen primary SI unit) and converting back. The library provides given instances for dozens of quantity types—`Mass` (in Kilograms), `Length` (in Meters), `Velocity` (in MetersPerSecond), `Temperature` (in Kelvin), and many more.

**Artemis:** Why not just use the Double-based distributions directly?

**Ophelia:** Because the types prevent errors. If you have `Uncertain[Length]` and `Uncertain[Time]`, dividing them should give `Uncertain[Velocity]`, not `Uncertain[Double]`. The squants module provides:

- `QuantityDistributionOps`: constructors like `Uncertain.normalQuantity(mean = Meters(100), stdDev = Meters(5))`, `Uncertain.uniformQuantity(min, max)`, `Uncertain.triangularQuantity(min, peak, max)`, and `Uncertain.quantityMeasurementWithError(value, absoluteError)` / `Uncertain.quantityMeasurementWithRelativeError(value, percentError)`.

- `QuantityArithmeticOps`: `+`, `-`, `*`, `/`, `abs`, `unary_-` for `Uncertain[Q]` where Q is a Quantity. Same-dimension addition and subtraction, scalar multiplication and division.

- Cross-dimension operations via `MultiplyOp` and `DivideOp` typeclasses: `Uncertain[Length].times(Uncertain[Length])` gives `Uncertain[Area]`. `Uncertain[Force].dividedBy(Uncertain[Area])` gives `Uncertain[Pressure]`. There are dozens of instances covering kinematics, dynamics, electromagnetism, density, and more.

**Artemis:** So the type system enforces dimensional analysis at compile time?

**Ophelia:** Yes. If you try to add `Uncertain[Length]` and `Uncertain[Mass]`, it won't compile. If you divide `Uncertain[Energy]` by `Uncertain[Time]`, you get `Uncertain[Power]`. The physics is checked by the Scala compiler.

**Artemis:** What about measurements with error? That seems like the most natural use case.

**Ophelia:** Exactly. Consider:

```scala
import squants.space.*
import squants.mass.*
import mostly.uncertaintee.squants.syntax.*

val length = Uncertain.quantityMeasurementWithRelativeError(
  value = Meters(100),
  percentError = 5.0   // ±5%
)

val width = Uncertain.normalQuantity(
  mean = Meters(50),
  stdDev = Meters(2)
)

val area = length.times(width)  // Uncertain[Area]
```

The `area` now properly propagates the uncertainty from both measurements, and its type is `Uncertain[Area]`—not `Uncertain[Double]`.

## Act XVII — Functional Programming Ops: sequence, traverse, mapN

**Artemis:** The core module provides some FP operations without requiring Cats. What's available?

**Ophelia:** The `FunctionalProgrammingOps` trait provides:

- **`Uncertain.sequence(list)`** — converts `List[Uncertain[T]]` to `Uncertain[List[T]]`. If you have three independent dice rolls, `sequence` gives you an uncertain list of three rolls. Correlations between the input Uncertains are preserved.

- **`Uncertain.traverse(items)(f)`** — maps a function over a collection where the function returns Uncertain, then sequences. Classic Haskell-style traverse.

- **`.product(other)`** — combines two uncertain values into a pair `Uncertain[(T, B)]`.

- **`.zipWith(other)(f)`** — combines and applies a function in one step.

- **`.collect(partialFunction)`** — like `filter` but with transformation.

- **`.flatten`** — for `Uncertain[Uncertain[T]]`, unwraps the nesting.

- **`mapN`** — applicative-style combination of up to 22 uncertain values via tuple extensions.

**Artemis:** Up to 22? That's a lot of overloads.

**Ophelia:** It is! The library manually defines `mapN` for tuples of arity 1 through 22 (matching Scala's tuple limit). The code comments acknowledge this is "a lot of boilerplate" but explain it as a reasonable tradeoff to avoid pulling in dependencies or writing macros. Each one simply chains `flatMap` and `map` calls.

```scala
val (w, h, d) = (uncertainWidth, uncertainHeight, uncertainDepth)
val volume = (w, h, d).mapN(_ * _ * _)
```

**Artemis:** That's the applicative pattern. And it works without Cats?

**Ophelia:** Yes—the core module is dependency-free. If you also pull in the Cats module, you get the *lawful* Applicative and can use Cats' syntax too. But for simple composition, the built-in `mapN` suffices.

## Act XIX — Approximate Equality and Distribution Comparison

**Artemis:** How do I compare two uncertain distributions? I can't use `==` since they're random.

**Ophelia:** The `ComparisonOps` trait defines an `ApproxEq[T]` typeclass for approximate equality. For basic types:
- `ApproxEq[Boolean]` — 0.0 if same, 1.0 if different
- `ApproxEq[Unit]` — always 0.0
- `ApproxEq[T: Numeric]` — absolute difference via `Numeric[T].minus`

For `Quantiles[T]`, it computes the maximum distance between corresponding quantile positions. There are two strategies:
- Non-numeric: rounds to nearest boundary (discrete comparison)
- Numeric: linearly interpolates between boundaries (continuous comparison)

And for `Uncertain[T]` directly:
- `.approxEq(other, threshold, sampleCount)` — samples both, computes percentiles, checks max distance
- `.maxDistanceTo(other, sampleCount)` — the maximum quantile-by-quantile distance

**Artemis:** So it's basically a Kolmogorov-Smirnov-like statistic?

**Ophelia:** Conceptually, yes. The maximum distance between quantile functions is related to the KS statistic. It's a practical measure for testing: "are these two distributions close enough?"

## Act XX — Performance and Design Philosophy

**Artemis:** Let me step back. What are the key design tradeoffs the library makes?

**Ophelia:** Several stand out:

**1. Lazy evaluation everywhere.** Nothing is computed until you call `sample()`, `mean()`, `percentiles()`, etc. The computation tree is built eagerly, but evaluated lazily. This means composing is cheap; only querying is expensive.

**2. No caching between sample calls.** Each call to `sample()` creates a fresh `SampleContext` and does a full tree traversal. This is intentional—caching would break the independence of successive samples. But it means repeated queries are O(samples × tree_depth).

**3. Correlation preservation over performance.** The `filter` design returning `Option` is slower and less convenient than rejection sampling, but it preserves the fundamental guarantee. The library consistently prioritizes correctness over convenience.

**4. Zero core dependencies.** The core module has no runtime dependencies at all. All integrations (Cats, Circe, ZIO, ScalaCheck, Squants) are separate modules. This makes the core lightweight and broadly compatible.

**5. Cross-platform.** The build defines both JVM and JS targets via `crossProject(JVMPlatform, JSPlatform)` with `CrossType.Pure`, meaning the code is pure Scala with no platform-specific APIs.

**6. Explicit sample counts.** Every statistical method requires you to specify `sampleCount`. This is a deliberate API decision—there are no hidden defaults that might give users a false sense of precision.

**Artemis:** That last point is interesting. Why not provide defaults?

**Ophelia:** Because the right sample count depends entirely on context. For a quick check, 1,000 samples might suffice. For a published result, you might want 1,000,000. For serialization via Circe, the Scaladoc recommends 100,000+. By making it explicit, the library forces you to think about the accuracy-performance tradeoff.

## Act XXI — The Implicit vs. Given Decision

**Artemis:** You mentioned the `WhyIsThisImplicitAndNotGiven` style document. This seems like a principled stance.

**Ophelia:** It is. The issue is that in Scala 3, `import foo.*` imports `implicit` vals but not `given` instances. To get givens, you need `import foo.{given, *}`. This was a deliberate design choice by the Scala team to reduce "implicit pollution," but it creates a migration headache for libraries.

The uncertain-tee library argues that wildcard imports should mean "everything"—that's what users expect. So all typeclass instances and conversions use `implicit` rather than `given`. The Scaladoc notes that they'll switch when a future Scala LTS drops the old behavior.

**Artemis:** It's a pragmatic choice. Documentation beats purity.

## Act XXII — Building Your Intuition: Real-World Patterns

**Artemis:** Let me try to synthesize. Give me some patterns I'd actually use.

**Ophelia:** Gladly.

**Pattern 1: A/B Testing**
```scala
val control = Uncertain.normal(0.08, 0.01)
val test    = Uncertain.normal(0.11, 0.015)
val improvement = test - control
if ((improvement > 0.0).probabilityExceeds(exceeds = 0.95, sampleCount = 10_000)) {
  println("Test variant is significantly better")
}
```

**Pattern 2: Risk Assessment**
```scala
val serverLoad = Uncertain.normal(0.65, 0.15)
val riskOfOverload = (serverLoad > 0.9).probability(sampleCount = 10_000)
println(s"Risk of overload: ${riskOfOverload * 100}%")
```

**Pattern 3: Dependent Decisions via flatMap**
```scala
val temperature = Uncertain.normal(20, 5)
val clothing = temperature.flatMap { temp =>
  if (temp < 10) Uncertain.categorical(Map("coat" -> 0.8, "sweater" -> 0.2))
  else if (temp < 25) Uncertain.categorical(Map("sweater" -> 0.6, "shirt" -> 0.4))
  else Uncertain.categorical(Map("shirt" -> 0.7, "t-shirt" -> 0.3))
}
```

**Pattern 4: Project Estimation with Confidence**
```scala
val total = frontend + backend + testing
val percentiles = total.percentiles(sampleCount = 100_000)
println(s"50% chance: ${percentiles(50)} days")
println(s"90% chance: ${percentiles(90)} days")
println(s"Probability of finishing in 30 days: ${(total < 30).probability(sampleCount = 100_000)}")
```

**Pattern 5: Mixture Models for Bimodal Data**
```scala
val userCount = Uncertain.mixture(Map(
  Uncertain.normal(50, 5)  -> 0.3,  // peak hours
  Uncertain.normal(15, 3)  -> 0.7   // off hours
))
```

**Pattern 6: Serialization Round-Trip**
```scala
val original = Uncertain.normal(50, 10)
val json = original.toJson(sampleCount = 100_000)
val Right(reconstructed) = Uncertain.fromJsonAsSmoothDistribution(json)
// reconstructed ≈ original
```

**Pattern 7: Domain Modeling with Case Classes**
```scala
case class SensorReading(temperature: Double, humidity: Double, pressure: Double)

val reading: Uncertain[SensorReading] = (
  Uncertain.normal(22.5, 0.5),
  Uncertain.normal(65.0, 3.0),
  Uncertain.normal(1013.25, 2.0)
).mapN(SensorReading.apply)
```

**Artemis:** These are all remarkably concise. The for-comprehension approach means the uncertainty is threaded through automatically, and I just write normal Scala code.

**Ophelia:** That is the ultimate design goal: *uncertainty should be as easy to work with as certainty*. You don't need to know statistics to use this library effectively. You model your inputs as distributions, compose them using the operations you already know—addition, comparison, for-comprehensions—and query the results via sampling. The library handles correlation, propagation, and statistical soundness under the hood.

## Act XXIII — Reflections: The Philosophy of Uncertain[T]

**Artemis:** If I had to summarize the philosophy of this library in a few sentences, I'd say it makes the following argument: "The world is uncertain. Your code should acknowledge that, not paper over it. And acknowledging it shouldn't require a PhD in statistics."

**Ophelia:** I think that's a faithful distillation. Let me add a few more threads:

**Composability over complexity.** The library is built on a small core—a sealed abstract class with `map`, `flatMap`, `filter`, `sample`, `take`, `iterator`—and everything else is extension methods. This means the core is trivially auditable, and the extensions can grow without making the core harder to understand.

**Correctness over convenience.** The `filter` returning `Option`, the explicit sample counts, the correlation preservation even at the cost of performance—these are all choices that prioritize getting the right answer over making the API easy.

**Modularity over monolith.** Six modules, one dependency-free core. You pull in exactly what you need. The Cats user doesn't pay for Circe; the ScalaCheck user doesn't pay for Squants.

**Accessibility over exclusivity.** `bellCurve`, `drawFromHat`, `oneIn`, `maybe()`, the dice-rolling vocabulary—these aren't frivolous. They're an invitation to non-statisticians to participate in probabilistic programming.

**Artemis:** And the paper-backed guarantee—correlation preservation via the computation tree—gives the whole thing a foundation that's not just "we tested it and it seems to work."

**Ophelia:** Indeed. The memoized computation tree isn't a heuristic; it's a provably correct mechanism. The same leaf ID always produces the same value within a single evaluation. Map fusion is semantics-preserving. Trampolining is stack-safe. These are engineering guarantees rooted in the mathematical semantics of the monad.
